# Docker 三容器部署架构理解（Nginx + NestJS + PostgreSQL）

## 架构图

```
公网用户
    ↓ HTTP/HTTPS 请求（80/443 端口）
┌─────────────────────────────────┐
│         Nginx 容器               │
│   反向代理 + 静态文件 + SSL        │
└────────────┬────────────────────┘
             │ 转发到内部端口 3000
┌────────────▼────────────────────┐
│         NestJS 容器              │
│       运行编译后的 dist/          │
└────────────┬────────────────────┘
             │ 内部网络连接
┌────────────▼────────────────────┐
│       PostgreSQL 18 容器         │
│         数据持久化存储             │
└─────────────────────────────────┘
             ↕ 挂载
┌─────────────────────────────────┐
│      Docker Volume（数据卷）      │
│   数据存在宿主机磁盘，容器重启不丢   │
└─────────────────────────────────┘
```

---

## 一句话总结

**一个请求从用户到数据库，经过了三层容器：Nginx 负责"接待"，NestJS 负责"干活"，PostgreSQL 负责"存数据"。**

每层只做自己擅长的事，通过 Docker 内部网络互相通信，外部只能接触到 Nginx。

---

## 每一层的作用

### 第一层：Nginx 容器 —— 「门卫 + 前台」

| 角色 | 说明 |
|------|------|
| **对外入口** | 公网用户只能访问到 Nginx（80/443 端口），其他容器不直接暴露到公网，更安全 |
| **反向代理** | 把请求转发给后面的 NestJS（内部端口 3000，外部访问不到） |
| **静态文件服务** | 前端打包好的 HTML/CSS/JS 直接由 Nginx 返回，比让 NestJS 来服务快很多 |
| **SSL / HTTPS** | 证书配置在 Nginx 上，负责加密解密，NestJS 不用管 HTTPS |
| **负载均衡** | 以后可以加多个 NestJS 实例，Nginx 自动分发请求 |
| **限流 / 缓存** | 可以在 Nginx 层做限流、静态资源缓存，减轻后端压力 |

> 为什么不直接让 NestJS 暴露 80 端口？
> - Node.js 处理静态文件效率低
> - SSL 配置在 Nginx 上更成熟、性能更好
> - Nginx 是专业的反向代理，稳定可靠
> - 后端服务不直接暴露在公网，更安全

---

### 第二层：NestJS 容器 —— 「业务大脑」

| 角色 | 说明 |
|------|------|
| **处理业务逻辑** | 用户注册、登录、发帖子、查数据……所有业务代码跑在这里 |
| **运行编译后的 JS** | 容器里不需要 TypeScript，只需要 `dist/` 目录下编译好的 JS 文件 |
| **连接数据库** | 通过内部网络连接 PostgreSQL，读写数据 |
| **返回 JSON 给前端** | 处理完业务，把数据通过 Nginx 返回给用户 |

> 容器里为什么只放 `dist/`？
> - 生产环境不需要源码，编译后的 JS 就能运行
> - 镜像体积更小，部署更快
> - 避免泄露源码

---

### 第三层：PostgreSQL 容器 —— 「数据仓库」

| 角色 | 说明 |
|------|------|
| **存储数据** | 用户表、帖子表……所有数据都存在这里 |
| **不对外暴露** | 只允许内部网络的 NestJS 连接，公网访问不到，更安全 |
| **数据持久化** | 数据不放在容器内部，而是挂载到 Docker Volume（宿主机磁盘） |

> 为什么数据不直接存在容器里？
> - 容器是"临时"的，删除容器数据就没了
> - Docker Volume 是宿主机上的目录，容器删了数据还在
> - 升级 PostgreSQL 版本时，只需要换容器，数据不动

## 一个请求的完整旅程

```
用户在浏览器输入 example.com/posts
          ↓
1. DNS 解析到服务器 IP
          ↓
2. 请求到达 Nginx 容器的 443 端口（HTTPS）
   Nginx 检查证书、解密请求
          ↓
3. Nginx 判断这是 API 请求，转发给 NestJS:3000
   （内部 Docker 网络，通过容器名访问）
          ↓
4. NestJS 收到请求，执行业务逻辑
   → 需要查数据 → 连接 PostgreSQL
          ↓
5. PostgreSQL 执行 SQL，返回数据给 NestJS
          ↓
6. NestJS 组装成 JSON，返回给 Nginx
          ↓
7. Nginx 把响应加密（HTTPS），返回给用户
          ↓
用户浏览器拿到数据，渲染页面
```

## Docker 内部网络是怎么通信的？

三个容器在同一个 Docker 网络里（比如叫 `app-network`），互相之间可以**用容器名当域名**访问：

```
Nginx 转发配置里写：
  proxy_pass http://nestjs:3000;
                           ↑
                    这里的 nestjs 就是容器名

NestJS 连接数据库写：
  DATABASE_URL="postgresql://user:pass@postgres:5432/mydb"
                                             ↑
                                       postgres 就是数据库容器名
```

不需要记 IP 地址，直接用容器名就行，Docker 内部有 DNS 解析。

## 为什么要用三个容器？不放在一个容器里？

这叫**单一职责原则**，每个容器只做一件事，好处是：

| 好处 | 说明 |
|------|------|
| **独立升级** | 想升级 PostgreSQL 版本？只换数据库容器，Nginx 和 NestJS 不用动 |
| **独立扩缩容** | 访问量大了，可以加多个 NestJS 容器，Nginx 做负载均衡 |
| **故障隔离** | NestJS 挂了不影响数据库，Nginx 还能返回错误页面 |
| **复用镜像** | Nginx、PostgreSQL 都是官方现成的镜像，不用自己从零做 |
| **安全分层** | 数据库不对外暴露，攻击面更小 |

反过来，如果把所有东西塞在一个容器里：
- 升级一个组件可能影响另一个
- 没法独立扩容
- 镜像又大又重
- 出问题排查困难

## Docker Volume 为什么重要？

容器是**无状态**的（stateless）——删了再建，里面的东西就全没了。

但数据库的数据必须是**有状态**的（stateful）——不能说删容器就把数据删了。

Docker Volume 就是干这个的：

```
容器里的 /var/lib/postgresql/data
        ↕（挂载）
宿主机上的 /var/lib/docker/volumes/my-postgres-data/_data
```

- 容器里读写 `/var/lib/postgresql/data`，实际写到了宿主机磁盘
- 容器删掉重建，Volume 里的数据还在
- 升级 PostgreSQL：删旧容器 → 建新容器 → 挂载同一个 Volume → 数据完好无损

## 快速记忆

| 容器 | 比喻 | 关键词 |
|------|------|--------|
| Nginx | 门卫 / 前台 | 入口、SSL、反向代理、静态文件 |
| NestJS | 业务大脑 | 逻辑、API、JSON |
| PostgreSQL | 仓库管理员 | 数据、持久化 |
| Docker Volume | 地下仓库 | 数据不丢、跨容器 |

记住一句话：**Nginx 接客，NestJS 干活，PostgreSQL 管账，Volume 管保险箱。**
